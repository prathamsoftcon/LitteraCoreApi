# Release Notes: 14–23 August 2026

## Scope

This release includes all commits on the `Tokenimplementation` branch after 13 August 2026, through commit `fbf064c` on 23 August 2026. It covers Training Master migration support, email/SMS delivery reliability, and OTP validation.

## Highlights

### Training Master migration

The API now supplies the remaining data needed by the React Training Master wizard:

- `GET /api/Trg_Payment_Type` returns payment types for the Payment step. Single and Joint types are excluded, and a synthetic **Sponsored** option is included.
- `GET /api/Trg_Sponsor_Agency` returns sponsor/paid-by agencies (agency type `00053`) without requiring the `PublicApiKey` policy used by the generic agency endpoint.
- `GET /api/Trg_Participant_Level` returns participant-level master data.
- `POST /api/RCVP_Participant_Level_Save_Data` creates or updates a participant-level record. The request body contains `levelId`, `levelDescription`, and `hLevelDescription`.

Participant levels use the existing database procedures `TrainingPlan.proc_get_participantlevel` and `Trainingplan.proc_tp_ins_upd_participantlevel`. The client continues to supply the level ID, matching the legacy behaviour.

### Email delivery and bulk mail

- SMTP host, port, username, and password now prefer application setting `7`, while retaining `emailSetting.xml` as a fallback for installations that have not migrated their settings.
- Mail service failures are logged and, by default, surface as `EmailDeliveryException`. Background registration and certificate notifications remain best-effort, so a notification failure does not undo a completed workflow.
- `POST /api/Send_Mail` now validates recipient, subject, and message. It returns `400 Bad Request` for invalid input and `502 Bad Gateway` when the provider rejects delivery.
- `POST /TRG_SEND_PARTICIPANT_MAIL` now removes blank and duplicate recipient addresses, waits for the send operations to finish, and returns the number sent. It returns `400` when no usable recipient is available, `502` for delivery failure, and `500` when preparation fails.
- Shared-content mail responses no longer expose provider exception details to callers.

### OTP and SMS handling

- OTP login, registration, and password/OTP flows now treat blank email or mobile values as missing. Sending occurs only when the corresponding OTP channel is enabled and a valid non-blank destination exists.
- Failed OTP email sends return a controlled `502 Bad Gateway` response and are logged rather than being silently ignored.
- `GET /api/Send_General_OTP` rejects a blank username, routes email identifiers through email and other identifiers through SMS, and reports controlled delivery failure instead of returning the OTP value.
- SMS delivery can now opt into throwing on provider failure; general OTP uses this mode so callers receive a failure response.
- User-creation email is attempted only when the address is non-blank, and remains non-blocking after the user record has been created.

## API compatibility notes

Clients should account for these intentional response changes:

| Endpoint | Previous successful response | New successful response |
| --- | --- | --- |
| `GET /api/Send_General_OTP` | The OTP value | `{ "message": "OTP sent successfully." }` |
| `POST /TRG_SEND_PARTICIPANT_MAIL` | `true` | `{ "sent": <recipient-count> }` |

The mail endpoints may now return structured `400`, `500`, or `502` responses where failure was previously not consistently reported. UI clients should display the returned generic `message` and must not assume email/SMS delivery after a non-success status.

## Deployment and verification checklist

- Confirm application setting `7` contains valid SMTP `host`, `portno`, `login`, and `password`; XML settings are only the compatibility fallback.
- Confirm application setting `6` enables the intended OTP channels (`OTP_ON_SMS` and/or `OTP_ON_MAIL`).
- Verify the two participant-level stored procedures are available in the target database.
- Smoke-test the four new Training Master endpoints and both General OTP delivery paths (email and SMS).
- Update frontend callers to consume the changed General OTP and bulk-mail response objects.
